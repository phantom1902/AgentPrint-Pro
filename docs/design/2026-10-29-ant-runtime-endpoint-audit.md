## 对当前设计的影响

Q20 曾按“必须有已有明确运行端信息，缺失跳过”记录。现场事实说明这不是已知仅影响少量异常样本的分支；按该严格口径，目前没有足够的直接身份依据来构造所需方向输入。

用户已选择 Q54=A：允许将 PCAP 中的地址/连接特征纳入识别依据，使用固定、可审计的规则识别运行端，无法明确时再跳过。这修订 Q20 原先不额外推断的限制，但不代表接受任何具体启发式、覆盖率阈值或多地址消歧方式。本报告不提供已验证的方向准确率；具体规则待报文样本核验后继续磋商。

其余已确认任务、标签、MTAM、损失、训练预算与工程选择保留。本报告是设计事实核验，不是预处理或训练完成报告。

## 报文内容抽样：运行端规则的证据

从训练集现有 26 个 engine×scenario 组合各取“有完整标注且 PCAP 最小”的一个 episode，覆盖 6 个引擎、5 类场景。两遍只读扫描相同 26 份文件，每遍 20165429 字节（合计约 40.33 MB）；26 份均完整读到文件末尾，无截断。样本共 36854 个 IP 包，不按两遍重复计数。这是偏向小文件的抽样，不代表全数据覆盖率或方向准确率。

- 22/26 出现两个 RFC1918 地址，不能使用“文件里仅有一个私网 IP”规则。
- 23/26 只有一个 RFC1918 地址发出 SYN=1、ACK=0 的 TCP 包。该地址同时是参与 IP 包数的唯一第一名，覆盖率 93.213%–99.774%。各主要 IPv4 地址的发包源 MAC 在相应文件内均唯一。
- 3/26 没有 TCP，主要 IPv4 端发出的 UDP 包目的端口均为 53。不能把它们记作满足 TCP 规则。
- 无环回 IP 包。26 份均有少量 IPv6，共 347 包，目的均为组播，源为 fe80:: 链路本地或 ::，无全球单播 IPv6。只有 67 包的源或目的 MAC 与主要 IPv4 端的源 MAC 匹配；不能将其余 IPv6 包全部归作该端下行。

候选基础规则：唯一发出 TCP 初始 SYN 的 RFC1918 地址，且它是参与 IP 包数的唯一第一名，则作为推断运行端；否则跳过。不添加覆盖率阈值，不按地址字典序消歧。此规则在抽样中可选择 23/26，尚未获用户确认。是否增加 UDP/53 请求端回退，以及是否用同一唯一 MAC 关联 IPv6 地址，见下一轮 Q58/Q59，均未自动采用。
